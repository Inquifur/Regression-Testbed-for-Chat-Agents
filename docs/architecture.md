# 架构与执行语义

## 从 JSON 到检查结果

CLI 负责递归发现 JSON 并按相对路径排序，校验结构、字段、时间和引用，拒绝跨文件重复的场景 ID。输入校验不依赖 Bot。运行时对每个有效场景创建新的虚拟时钟、适配器实例和内存输出收集器；上一个场景的冷却、上下文和额度不会进入下一个场景。

每个事件顺序固定：

1. 将 `VirtualClock` 推进到 `at_ms`。
2. 等待 `on_tick()`，清理当前时刻过期状态。
3. `message` 事件等待 `handle_message()`；`advance` 不调用消息处理。
4. 保存本步骤决策、输出和状态快照。
5. 执行所有 `after_event` 指向本事件的检查。

同一时间戳按文件顺序执行；非法时间顺序不会被排序掩盖。场景内所有异步调用顺序等待，无并发消息、后台任务、真实 sleep 或定时回访。

## 时间与状态

业务时间从 0 开始，以非负整数毫秒表示；布尔值、浮点数和倒退均被拒绝。冷却是严格小于间隔时拦截，窗口是左开右闭，TTL 是达到寿命时删除。这些边界均由虚拟时钟决定，运行速度和操作系统时钟不会改变结果。

每个群独立存放状态，群上下文表示为 `groups[group_id].context_message_ids`。快照是 JSON 可序列化的深拷贝，报告保存后不能被后续事件或 `close()` 改写。输出 sink 仅收集内存消息，运行器决定当前 `event_id`、`at_ms` 与稳定输出 ID；适配器不能声称输出来自另一事件或群，tick 阶段也不能发消息。

## 适配器边界与能力

`BotAdapter` 使用 `start(config, clock, sink)`、`on_tick()`、`handle_message(event)`、`snapshot()` 和 `close()` 协议。Factory 必须每场景创建全新对象。清理位于 `finally`，即使启动或执行异常也尝试关闭资源；异常记录为结构化错误，并将本场景剩余检查标为 `not_run`，再执行其他场景。

四种可观察能力独立声明：

| 能力 | 可观察信息 |
| --- | --- |
| `outputs` | 被 sink 收集的 Bot 输出 |
| `decisions` | `should_reply`、`reason` 等结构化决策 |
| `context_ids` | 当前各群上下文消息 ID |
| `selected_context_message_id` | 本条输入路由到的上下文消息 ID，允许 `null` |

缺少检查所需能力时返回 `unsupported`，不算通过。真实 Bot 无需伪造它无法提供的内部信息。声明了能力却提供错误的数据类型、错误事件归属或非 JSON 数据属于适配器错误。声明上下文能力时，尚未创建的群按空上下文处理。

## 断言与确定性

检查只支持输出计数、决策白名单字段相等、上下文包含/排除四类，不执行用户输入代码。行为失败保留预期和实际值，并继续本场景其他检查。执行错误与行为失败单独存储，输入/执行/写报告错误的退出码高于普通失败。

报告按稳定输入顺序和稳定序列化规则输出，不引入墙钟时间、随机标识符或平台性能值。相同输入和适配器应产生相同报告，可直接比较内容。

测试关注结构化决策，不比较自然语言逐字输出：真实模型措辞变化不必然表示行为回归，固定文本相同也无法证明冷却、隔离或上下文正确。V1 的 `测试回复` 是演示夹具的固定输出，工具不判断自然度、事实性或多人话题理解能力。
